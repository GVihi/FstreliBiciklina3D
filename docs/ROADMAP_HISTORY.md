### Fix: rubber banding when the player hugs a building wall (`slide_walk`)

### Rider pursuit steering: ride toward the player on any open surface, pass, then turn round in a smooth arc and return; spawning at gates

`Arena.rider_pursuit()` switches it on, so an arena that says yes gets it and the roundabout, which says no, keeps its lanes; the code is in `scripts/riders.gd`. A rider comes out of one of the arena's gates (drawn with the seed) facing in, rides at the player, and once the player is behind it and within 7 m it rides straight on for 9 m, then swings round and comes back, pass after pass. The turn is limited by sideways acceleration (`PURSUIT_ACCEL` 20 m/s², at most 6 rad/s), so a fast rider swings wide (a turning circle of speed squared over 20 m) and a slow one turns tight, never a snap. It rides at its speed times the share for the ground under it (`Arena.rider_speed_at`, the `rider_speed` table in `data/arena_rules.json`: road and plaza 1.0, sidewalk 0.9, grass 0.75). ## Technical Refactor (Recommended Before Milestone D) › Future-Proofing

### Make weapon additions easier

A weapon is now one entry of `data/weapons.json`. Before, adding the Marshmallow Blaster meant edits in six places: the numbers, a duplicate of them in `FALLBACK` in `scripts/weapons.gd` (plus the weapon names in three error messages), `PRIMARY_WEAPONS`, `SHOT_SOUNDS` and `WEAPON_INFO` in `scripts/weapon_slots.gd`, and the `guns` table in `main.gd`. Now each entry carries an `info` object (`slot`, `hud`, `name`, and optional `desc`, `sound`, `model`) next to its numbers, `Weapons.load_all()` returns numbers and info together, and `weapon_slots.gd` builds `PRIMARY_WEAPONS`, `MELEE_WEAPONS`, `GADGET_WEAPONS`, `WEAPON_INFO` and `shot_sound()` from it. `main.gd` builds a first-person model for each primary weapon through the new `Models.build_viewmodel(key)`; a weapon with no model key is shown with the default weapon's model. The same file now serves all three slots, so a melee weapon or a gadget is an entry with `"slot": "melee"` or `"gadget"`. A number left out takes the value of the slot's base weapon (dart pistol, gummy worm) and a gadget needs `uses` and/or `cooldown`; the built-in `FALLBACK` shrank to the two weapons every run needs. `data/README.md` has an "Adding a weapon" section with the steps, and the README's "A new weapon is done when" list no longer asks for an entry in `weapon_slots.gd`.

Decisions (first guesses): (1) the weapon `info` lives in the same file as the numbers, so one entry is the whole weapon; (2) the order of the file is the order on the Loadout page after the slot's default; (3) the gadget numbers `uses` and `cooldown` are a guess made before any gadget exists, and the first gadget may rename or add to them (`OPTIONAL` in `weapons.gd` is where a new number goes); (4) if a weapon other than the two defaults has a broken `info`, it is left out and logged, not fixed up. The public API of `WeaponSlots` and `Weapons.load_table()` did not change, so saves and the other checks needed no change.

Checked: new `tools/weapon_registry_check.gd` (the shipped file against the slot tables, sounds, models and weapon unlocks; a made-up file with a new primary weapon, melee weapon and gadget that load, take the base values, and work in a game with no code change; broken entries left out; a missing or invalid file still gives the two default weapons; broken once on purpose with a wrong sound name and it failed), plus `weapon_slots`, `loadout`, `unlocks`, `offer_sense`, `marshmallow_blaster`, `dart_pistol`, `run_save` and `reload`; gdlint and gdformat clean, Godot 4.7. Not covered: **melee weapons with their own model or swing**: the melee viewmodel (`rubber` in `main.gd`, animated in `scripts/player.gd`) is still one worm, so a melee variant with its own look needs the audit item under "New Melee Weapons" first; and **gadgets**, whose use key, HUD slot and effects are still the "Gadget use key" and Stink Bomb items. The relic half of the roadmap line is not done: no relic system exists yet.

### V1.2 `secrets.example.cfg` and the loader

Built on branch `roadmap/v1-1-gitignore` (the same branch as V1.1, at the owner's request, so it comes after the V1.1 commit and not from `main`). What it does: `Secrets.get_value(section, key, default)` returns a value from, in this order, the environment variable `FB3D_<SECTION>_<KEY>` (`FB3D_API_BASE_URL`, `FB3D_API_KEY`) and then the untracked `secrets.local.cfg` in the project folder (a copy of the template; `secrets.local.*` has been git-ignored since V1.1). The template holds the two values V3 and V4 will read, the API base URL and the key, both fake. `Secrets.KNOWN` lists what the game reads; a new value is added there and in the template, and the check compares the two. `status_line()` gives one log line that names where each value came from and never the value.

Rules, each one covered by the check: (1) nothing is required: no file and no variable is the normal state of a fresh clone and gives the default (an empty string); a missing, empty, damaged or oversized file, an unquoted or wrong-typed value and a value over 512 characters all count as "not set" and never stop the game. (2) A value that still looks like the template (starts with `fake`, contains `.invalid` or `replace-me`) counts as not set, so an unedited copy never sends a fake key; a template value in the environment does not hide a real one in the file. (3) Nothing is read unless the game runs from the Godot editor binary (`Secrets.allowed()`, the same rule as `--dev-coins`): an exported game never reads this file or these variables and gets its values from the build (V4.1). (4) Nothing prints a value.

Decisions (first guesses, the owner can change them): (a) **Editor only.** The roadmap item only says "an untracked file or an environment variable"; reading them in an exported game too would let anyone point a tester's exe at another server with one variable, which V4.1 already rules out for `--dev-api`. V4.1 decides how an exported build gets its key. (b) **Own small reader instead of Godot's `ConfigFile`.** The first version used `ConfigFile`, and the check log showed that on a damaged file Godot prints an `ERROR: ConfigFile parse error ...` line; such a message can name part of the broken line, which may be a key. `Secrets.parse_text` reads `[section]` lines, `key="text"` lines (with `\"` and `\\`), `;` and `#` comments, a byte order mark and Windows line ends, and skips every other line without a word. The check confirms that it reads the template exactly as `ConfigFile` does. (c) The two variable names are derived from the section and the key, so they are not listed anywhere else; the template names them in its comments and the check fails if one is missing.

Checked: `python tools/run_checks.py --lint secrets_loader version dev_start` passes (Godot 4.7 headless, gdlint and gdformat clean), and the log of `secrets_loader_check` holds no `ERROR` line. The check covers: nothing set, the file, the environment winning, trimming, a template value in either place, 11 kinds of bad file (empty, garbage, half a section, wrong section, number, array, blank, too long, unquoted, no section, file over 64 KB) and a folder in place of the file, the real process environment (`OS.set_environment`), the `allowed` gate, the status line holding no value, the template (every known value present and fake, nothing unknown, the same reading as `ConfigFile`), and `.gitignore` ignoring `secrets.local.*` without hiding the template. Each rule was then broken once on purpose and the check failed every time (gate removed, template values counted as real, the file ahead of the environment, the value in the status line, no length limit, unquoted values accepted, no file size limit, no byte order mark skip, no escapes, no trim); one of those tests was too weak at first (the byte order mark stood before a comment, where it does no harm) and was fixed until the break was caught.

Not covered: nothing calls the loader yet (`web_api.gd` in V4.1 will), so the game itself is unchanged and no other check was affected. I could not run an export (no export templates here), so that `secrets.example.cfg` and a stray `secrets.local.cfg` are left out of the exe was reasoned from the preset (`export_filter="all_resources"` with `include_filter="data/*.json"`) and not tried; look at it at the first export (V2.5). ### V1.4 `tools/secrets_check.py`

Built on branch `roadmap/v1-1-gitignore` (the same branch as V1.1 and V1.2, at the owner's request, so it is the third commit on it). New file `tools/secrets_check.py` (Python standard library only, so it runs on Windows too); `README.md` got the one-line install step under "Secrets and credentials" and the ticks (this item, and "Add a pre-commit check" in Milestone N "Keeping secrets out of the public repository"). It is not a `*_check.gd`, so `python tools/run_checks.py` does not run it; its own test is `python tools/secrets_check.py --self-test`. No `.bat`, as the testing rule of 2026-10-27 says.

What it does: `python tools/secrets_check.py` reads `git diff --cached` (the lines a commit ADDS; deleted and unchanged lines are not looked at) and the staged file names, prints `path:line: kind of finding` and exits 1 on any finding (0 clean, 2 when git could not be read). It never prints the line or the value, and the report names no variable either. The rules: a private key block; a secret-sounding name (`api_key`, `secret`, `password`, `passphrase`, `token`, `private_key`, the `X-FB3D-Key` header) given a literal value, quoted or in `NAME=value` form, where a placeholder (fake, example, changeme, replace, `<key>`, `${KEY}`, the name itself, repeated characters), a call, a variable, a URL or path and a too short value are not counted; the well-known token formats (AWS, GitHub, Slack, Google, Stripe, JSON Web Token); a password inside a URL; a 32+ character random-looking string (base64-like, three of four character classes, entropy 4.2 or more, not a written-out alphabet and not a path, URL or `base64,` data); and a staged file whose name says key or secret (`.env`, `secrets.local.*`, `*.pem`, `*.key`, `*.pfx`, `*.p12`, `*.crt`, SSH key names, `export_credentials.cfg`, `local_settings.py`, token and credential files, `api_key.*`), which means someone forced it past `.gitignore`. `.env.example` and `secrets.example.cfg` are allowed. Skipped on purpose, because they hold long machine-made strings: `*.import`, `*.uid`, `*.tscn`, `*.tres`, `*.scn`, `*.res`, `*.svg`, `*.lock` and `docs/baseline_f1/`. A deliberate fake (a test, an example) carries `secrets-check: ignore` in a comment on that line.

`--install-hook` writes `.git/hooks/pre-commit` (the folder `git rev-parse --git-path hooks` names, so a worktree or `core.hooksPath` works): it tries `python3`, `python` and `py` and uses the first one that really runs (on Windows a Microsoft Store stub can hide behind the name `python3`), and when none runs it stops the commit with a message and says how to skip once (`--no-verify`). It is safe to run twice, and it never overwrites a different pre-commit hook; it says so and tells the owner to add the line by hand.

Decisions (first guesses, the owner can change them): (1) the hook **fails closed**: no working Python stops the commit instead of letting it through unscanned. (2) The skip list and the entropy limit are tuned on this repository; a finding that is a false alarm gets the `secrets-check: ignore` comment, not a bigger skip list. (3) A hex key with no name next to it is not found (hex text has two character classes, which is what lets git SHAs and SHA-256 checksums pass in the docs); a named one (`api_key = "..."`, `FB3D_API_KEY=...`) is. (4) It scans what is staged, not the history or a branch; V1.5 (CI over a pull request) needs a way to name a range, and V1.6 (the history) a walk over old commits, and both are left for those items. The self-test, the diff reading and `scan_diff` are separate functions so they can be reused.

Checked, with Python 3.13 and git 2.43 (flake8 and black clean at 120 characters): `--self-test` runs 21 made-up secrets that must be caught (each known format by its own rule, so that the generic random-string rule cannot hide a broken one), 24 clean texts that must pass (calls, variables, placeholders, the template's fake values, git SHA-1 and SHA-256 text, long URLs and paths, long identifiers, a data URI, an `ignore` line), the scanner's own file (it is committed through its own hook, so it must pass; this found real false alarms in its first version: the word `password` as a placeholder password, an alphabet constant, and fixture labels containing the word token), the diff reading (file names, line numbers, deleted files, a new file, deleted lines not scanned, skipped paths), 13 file names, and an end-to-end run in a throw-away git repository: a staged secret gives exit 1 and the output holds neither the value nor the line, the installed hook stops a real `git commit` with a secret and lets a clean one through, installing twice is fine, and a different hook is left alone. The scanner was run over the whole committed tree at `e61fba6` (492 files): 0 findings, so it does not cry wolf on the current files. Each rule was then broken once on purpose (19 breaks: every rule above, every known format one by one, the ignore marker, the skip list, line numbers, the exit code, the staged-only reading, the hook doing nothing, a different hook being overwritten, the value being printed) and the self-test failed every time. Two of those first runs were wrong tests of mine (the break did not change anything) and one showed a real gap (the GitHub, Google and Stripe format rules were hidden by the random-string rule), which is why the self-test now requires each format's own rule. A dead branch for hex strings was removed for the same reason.

Not covered: the hook was only run on Linux; whether it works under Git for Windows' own `sh` waits for the **Owner** on a Windows machine (run `python tools/secrets_check.py --install-hook`, stage a file with a fake `api_key = "..."` of 20 random letters, and `git commit`; it must stop). It is a heuristic: a determined or unlucky secret (a short password with no name, a hex key with no name, a key split over two lines) gets through, which is why V1.3 (GitHub push protection) and V1.5 (CI) are the other layers. Nothing waits for an in-game check.

### V1.5 CI runs the same scan on every pull request

DRF authenticates before it throttles, so a rejected key would never be counted, and the contract promises that a call with a rejected key counts against the per-IP limit. The key is checked in `ApiView.initial` right after the throttles instead. V5 has to run the bearer token step after it. (2) The key is checked **before** the version and build headers, the method and the body, so a caller without a key learns nothing else (a `POST` to `ping` without a key is `key_missing`, not 405, and its body is never read). Unknown paths, plain HTTP and a body over the hard limit are still answered first, because they need no key. (3) HMAC with a server-side secret was chosen over a slow hash, because the keys are 256 bits of randomness made by the server, so there is nothing to brute-force, and a slow hash on every call would let an attacker spend the server's time with wrong keys. The cost is one more secret for the owner to set (`FB3D_API_KEY_PEPPER`, listed in `docs/SECRETS.md`) before the first key is made; changing it later invalidates every key. (4) "Last used" was added to the key table because `docs/SECRETS.md` says the owner checks whether the old key is still in use before switching it off during a rotation, and nothing else recorded it. (5) The new model's admin texts are in Slovenian like the rest of the `fb3d` admin. (6) Milestone N "Be honest about the limit in the docs" is ticked because `docs/WEBSITE_API.md` says it plainly (since V3.2, repeated in the V3.4 text); the rest of that sentence (validating scores and saves, rate limits per account) is the work of later items. The owner can untick it.

Checked: `python manage.py test fb3d.test_api fb3d.test_api_key` runs 63 tests and passes (the 31 tests of V3.3, which now send a key, and 32 new ones), on Django 6.1.1 and DRF 3.18.3 with SQLite (not PostgreSQL): the two error codes and their statuses; wrong shape with no database query; a prefix or extension of a real key; switched-off and expired keys at once; two keys active and one switched off; a hash made with another pepper; the order against the version headers, the method and the body; a wrong or missing key counting against the IP limit, and the limit stopping a good key after that; no key in any response, cookie or log and nothing written to the errors log; no pepper failing closed without the key in the log; "last used" written at most once an hour; and the admin: the key shown once and found nowhere else (list, edit and history pages, the log entry, cookies), the hash not shown or editable, the switch actions, and a staff user without superuser getting 403. `makemigrations --check` finds nothing more and `migrate` applies `0003_gamekey` from scratch. The whole `fb3d` suite runs 82 tests with the same one failure as in V3.3, `test_only_author_can_read_edit_delete` (an `Http404` in a view makes `ErrorLoggingMiddleware` write to the `errors` database, which the test is not allowed to touch); it also fails on the owner's unchanged `web.zip` and was not changed. Not covered: nothing ran against PostgreSQL, gunicorn or nginx, so the **Owner** deploys it (set `FB3D_API_KEY_PEPPER` in the site's `app/.env` first, `python manage.py migrate fb3d`, restart gunicorn, then the `curl` checks in the site's `docs/WEBSITE_API_SITE.md`). The first real key is V3.5. No limits per key exist yet (only per IP and per account), and Milestone N's other API key items still wait for V3.5, V4.1 and V10.4.

## Web Integration Roadmap (v0.3.0) › V4. Knowing about updates

### V4.1 `scripts/web_api.gd`, the one place that talks to the website

Built on branch `roadmap/v4-1-web-api`, from `main`. New: `scripts/web_api.gd`, `scripts/api_key_file.gd`, `tools/api_key_file.py` (with `tools/api_key_file_cases.json`) and `tools/web_api_check.gd`. Changed: `tools/build_release.py`, `scripts/build_info.gd` (a public `header_text()` for the `X-FB3D-Build` header), the `include_filter` of `export_presets.cfg`, the CI `build_info` job, `docs/WEBSITE_API.md`, `docs/SECRETS.md`, `docs/DEVELOPING.md`. `README.md` ticks V4.1 and the Milestone N item "Store the key encrypted" (server side V3.4, game side here).

What it does: `WebApi` is a Node. `await web_api.request_api("GET", "releases/current")` gives one Dictionary with a result type (OK, OFFLINE, TIMEOUT, UNAUTHORIZED, KEY_REJECTED, UPDATE_REQUIRED, SERVER_ERROR), the status, the API's error `code`, `retry_after`, a `conflict` flag for the 409 of the saves, and the parsed `data`. Headers are the four of V3.2, the bearer token only when one is passed. The address and key come from `api_key.bin` in an exported game; an editor run may also use `--dev-api=URL`, `secrets.local.cfg` or the environment. With no address or key nothing is sent (OFFLINE, "not_configured"); `enabled = false` (the ONLINE FEATURES row of V4.4) sends nothing either. `tools/build_release.py` writes `api_key.bin` from `FB3D_API_KEY` and `FB3D_API_BASE_URL` just before the export and deletes it afterwards, also after a failed export; alpha and release builds refuse to build without the key unless `--no-api-key`. The file is XOR with a SHA-256 key stream plus a check, so the key is not a readable string in the exe, and `api_key.bin` is in the preset's `include_filter` (`api_key.*` was already in `.gitignore`).

Decisions (first guesses, the owner can change them): (1) **Not threaded.** Godot 4.7.2's threaded `HTTPRequest` does blocking reads: against a server that accepts the connection and then says nothing, its own 5 s timeout fired late and `cancel_request()` blocked the whole game for 20 s (until the server answered). Without threads the timeout fires at 5.003 s and the longest frame stays at a few milliseconds. V6's big download needs its own decision. (2) The 5 s timeout, 1 MiB response limit and 256 KiB request limit are first guesses. (3) Plain http is accepted only for `127.0.0.1` and `localhost` and only in an editor run, so V4.2's fake server needs no TLS; an exported game takes only https, even from its own build file. (4) An answer that is not 2xx and has no usable `code` is SERVER_ERROR, except 426 and 503; 401 and 403 without a code are not guessed. (5) `tools/build_release.py` checks the key's shape (`fb3dk_` and 43 characters) and the address at build time, so a typo is found on the build machine and not by a player. (6) The file is obfuscation, not protection, and the docs say so.

Checked: `python tools/run_checks.py web_api` (new, 397 checks) passes with Godot 4.7.2 here, and so do `version`, `version_compare` and `secrets_loader`. It reads the error table of `docs/WEBSITE_API.md` and fails when a code is missing from the game or maps to another type, so the doc and the game cannot drift apart. It also covers answers of every kind (damaged and non-object JSON, unknown codes, redirect, oversized body, `retry_after` from body and header), addresses, paths and header text, the source order of the address and key, a damaged key file never half used, the shared key file cases (the bytes Python writes are read by the game), that no print can show a secret, that only `web_api.gd` opens a connection, and that the key file is git-ignored and exported. Eight deliberate breakages (a changed mapping, http always allowed, a print with the key, the preset without the file, `.gitignore` without it, a changed doc table, redirects on, disabled still sending) were each caught. `python tools/api_key_file.py --self-test` and `python tools/build_release.py --self-test` pass; `gdlint` and `gdformat --check` are clean. A throw-away local server (not committed) was also called for a 200, 204, 403, 426, 429 with `Retry-After`, a redirect, a 1 MiB body, damaged JSON, a dropped connection, a POST with a token and a server that never answers; every one ended in the right type, and the headers on the wire were as specified.

Not covered: nothing was run against the real website or over https (no key exists on this machine), and no real export was made, so that `api_key.bin` really ends up in the exe waits for the **Owner** at V4.3 or V6.2 (set `FB3D_API_KEY` and `FB3D_API_BASE_URL`, run `python tools/build_release.py --channel alpha`, then unpack and look for the file in the pck). Nothing calls `WebApi` yet: V4.4 wires the update check and the ONLINE FEATURES setting, and the fake server of V4.2 and the full check V4.7 test the same code against a real socket, including a frozen server.

### V4.2 `tools/fake_api_server.py`, the pretend website

Built on branch `roadmap/v4-1-web-api` again (the owner asked to continue there, and V4.1 is not merged yet, so the branch holds both). New: `tools/fake_api_server.py`. Changed: `README.md` ticks V4.2 (the V4 parent stays open), the CI `build_info` job runs the self-test, `docs/DEVELOPING.md` (how to run it by hand and from a check), `docs/WEBSITE_API.md` (a short section saying that the game's checks trust the fake server, so a change to the contract changes both) and this file.

What it does: a standard library only HTTP server on `127.0.0.1` that plays `ping` and `releases/current` of `docs/WEBSITE_API.md`. Six scenarios, chosen at run time: `current` (the real site's order of checks: unknown path, body over the limit, key, version headers, method; the one error shape; `update` as `none`, `available` or `required` from the caller's `X-FB3D-Version` with `tools/version_compare.py`, with the published and the minimum version settable, or no release at all), `wrong_key` (403 `key_rejected` on every call), `slow` (the honest answer after a delay of up to 60 s; more than the game's 5 s is a silent server), `server_error` (500), `damaged_json` (200 with a body cut off in the middle) and `dead_connection` (the request is read, then the connection is closed with no answer). It counts every request that is not a control call, also one that got no answer, and keeps the last 100: method, path, scenario, the status sent (0 for none), whether the key was ok, wrong or missing, whether an Authorization header came, the version and build headers, the header names and the body size. A check starts it with `--ready-file PATH --lifetime 120`, reads the port and the key from that file, steers it with `POST /__fake__/scenario`, `reset` and `stop` and reads `GET /__fake__/stats`; those paths are made of characters `WebApi.is_valid_path` allows, so the game's own `WebApi` can make the control calls when its base address is the server's root.

Decisions (first guesses, the owner can change them): (1) **The key is made up for each run** (`fb3dtest_` and 43 random characters), is written only to the ready file and is never printed. A tracked literal key would trip `tools/secrets_check.py`, and a printed one would sit in every check log. `--key` is for a developer by hand and refuses a key of the real shape (`fb3dk_...`) and one the game would ignore as a template (`fake`, `.invalid`, `replace-me`). (2) **Control through paths on the same server** (`/__fake__/`) and not a second port or a command per scenario, so that a Godot check needs no socket code of its own. (3) **A failure scenario overrides everything**, including the key check, so `wrong_key` is "always 403" and not "403 for a wrong key". The honest scenario also rejects a wrong key, as the real site does. (4) **Only what V4.2 names is built.** Answers V4.7 will want that are not in the list (426, 429 with `Retry-After`, 503, a body over 1 MiB, wrong types in a valid body) and the calls of V5 and V8 are one more route or scenario each, added when the item that needs them is built; the route table and the scenario list are the only places to touch. (5) It listens on `127.0.0.1` only and has no option for another address; the game accepts plain http only for that address in an editor run. (6) `--lifetime` is 300 s by default (0 = never), so a crashed check leaves nothing running. (7) The answers always close the connection and always have a full HTTP/1.1 status line (on Python 3.12 `http.server` writes no status line for a request it cannot read unless told otherwise; 3.13 does it by itself).

Checked: `python tools/fake_api_server.py --self-test` runs 107 checks in about 4 seconds and passes on Python 3.11, 3.12 (the version CI uses) and 3.13; `ruff check --select F,E9` is clean. It covers every answer of `ping` and `releases/current` and their fields, the update state for seven caller versions against a release and a minimum, no release, the order of the checks (no key and no version is `key_missing`; a wrong method without a key is `key_missing`), every bad version and build header, 404 and 405 and 413 and an unreadable request line (always JSON, never HTML), the control calls and what each refuses, all six scenarios including a client that gives up on a slow call while the server still answers others, the counters and the 100-record and 100-path limits, that no key, wrong key or token is in `stats` or in anything the program prints, and the program as a child process (ready file, stop call, lifetime, the refusals to start). Ten deliberate breakages were each caught by a failing check: the key checked after the version headers, the key kept in `stats`, a dead connection that answers, control calls counted, an unknown path that needs a key, the minimum version ignored, listening on all interfaces, a wrong key accepted, the slow wait that ignores a stop (this one first **survived**: a daemon thread never delays the exit, so "stop returns quickly" proved nothing, and a check that no handler thread is left behind was added), and the missing status line (caught on 3.12, not on 3.13, which is why the self-test has to run on 3.12 in CI).

Not covered: **no Godot binary was available in this session, so the game's `WebApi` was never run against this server.** What `HTTPRequest` makes of `Connection: close` answers, the dead connection and a 30 s silence is expected from the V4.1 throw-away server (which was measured with Godot 4.7.2) but is not tried against this program; V4.7 is the item that does it. Nothing ran on Windows; the code uses threads, `os.replace` and no signals so that it should, and the **Owner** can run `python tools\fake_api_server.py --self-test` once to be sure. The server is not a model of the real site's security (no throttling, tokens or database) and it has no TLS.
